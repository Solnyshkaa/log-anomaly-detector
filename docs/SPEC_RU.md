# Техническое задание

**Тема:** Machine-Learning-Based Log Anomaly Detection System for Small Organizations
**Тип продукта:** локальный прототип мониторинга системных журналов небольших организаций
**Среда:** Python 3.12, pandas, scikit-learn, Ubuntu VM, GitHub. PyCharm или VS Code для разработки. HTML и CSV для отчёта.

## 1. Проблема и исследовательский вопрос

Небольшим организациям часто сложно вручную просматривать журналы и вовремя замечать необычные серии событий. Один из подходов — агрегировать журналы, оценивать отклонение от обычного поведения и показывать оператору интервалы для проверки.

**Исследовательский вопрос:** как Isolation Forest и простое пороговое правило отличаются по precision, recall, F1 и average precision при выявлении аномальных блоков Loghub HDFS_v1 на одной тестовой выборке?

Интерпретация результатов зависит от источника событий и уровня агрегации. Разметка HDFS фиксирует аномалии блоков файловой системы. Для Ubuntu собираются наблюдения и заранее отмеченные учебные сценарии.

## 2. Цель и задачи

**Aim.** To develop and evaluate a lightweight system that collects system logs and flags unusual activity for review.

1. Подготовить импорт двух источников: Loghub HDFS_v1 и системный журнал собственной Ubuntu VM.
2. Выделить числовые признаки по блокам HDFS и пятиминутным окнам Ubuntu.
3. Реализовать Isolation Forest и сравнить его с порогом по числу предупреждений и ошибок на размеченных данных.
4. Показать предупреждения и их причины в локальных отчётах.
5. Проверить воспроизводимость эксперимента и описать ограничения системы.

## 3. Архитектура и требования

| Компонент | Вход | Выход и критерий приёмки |
|---|---|---|
| Экспорт журнала | Интервал времени, Ubuntu VM | JSONL, успешный экспорт хотя бы одного реального периода; ошибка при пустом выводе |
| Парсинг Ubuntu | JSONL journalctl | UTC, число записей, предупреждений, ошибок и неудачных SSH-аутентификаций; число пропущенных записей выводится |
| Подготовка Loghub | HDFS.log и anomaly_label.csv | По одной строке на размеченный блок, присутствующий в логе; разметка исключена из признаков |
| Модель | Числовые признаки нормальных наблюдений | Isolation Forest с фиксированным random_state=42 и оценкой необычности на каждом наблюдении |
| Калибровка | Отдельные нормальные наблюдения | Порог по квантилю; исходная целевая доля сигналов 5%; измеренная доля записывается при оценке HDFS |
| Правило для Ubuntu | Число неудачных SSH-аутентификаций | При пяти и более записях в одном окне формируется сигнал; порог фиксирован для текущей версии |
| Отчёт | Пятиминутные окна Ubuntu | CSV и HTML с UTC-временем, признаками, оценкой, порогом и отдельными флагами модели и правила |
| Оценка HDFS | Размеченная тестовая часть | JSON с precision, recall, F1, average precision и TN/FP/FN/TP для модели и правила |
| Расписание | Ubuntu VM, базовый период, рабочий интервал | В итоговом варианте планировщик вызывает экспорт и анализ по расписанию, проверяется повторный запуск |
| Воспроизводимость | Репозиторий и ссылки на источники | Новый пользователь запускает demo по README. В отчёте указаны версии, источник, параметры и числа наблюдений |

Поток мониторинга: экспорт журнала → разбор JSONL → агрегация по 5 минут → оценка Isolation Forest и отдельная проверка правила → HTML/CSV. Поток исследования HDFS выполняется отдельной командой и обучает отдельный экземпляр модели.

Нефункциональные требования: локальный запуск без сетевого сервиса, чтение только журналов в пределах задания, отсутствие сырых логов и секретов в Git, отсутствие персональных идентификаторов в итоговом отчёте Ubuntu, отслеживание версии кода. Зафиксировать время выполнения и объём данных после реального прогона. Задать целевой интервал запуска после измерения времени на VM.

Ограничения: одна Ubuntu VM в прототипе; агрегирование теряет порядок событий; отсутствие событий в окне и недоступность журналов нельзя различить только по данным; правила разметки HDFS могут влиять на сравнительную оценку; случайное разбиение блоков HDFS оценивает обобщение внутри набора и может учитывать строки, общие для разных блоков. Для более строгой оценки рассмотреть временное или групповое разбиение. Особенности источника и изменения нагрузки влияют на ложные сигналы. Поддержка Windows, центральный сервер, обучаемые последовательностные модели и интеграции с внешними системами остаются расширениями.
